Settings, simplified

A proposal to rework the Settings window into five pages built from one row pattern, one card style and one accent colour.

Proposal, not built · Settings window · drawn 2026-09-23 against main at eec4b06 (v1.11.1)

1. The proposed window

Every setting is one row: a name and one short line on the left, one control on the right. Changes apply at once. There are no Save buttons, no eyebrows, no page intros and no model cards. The window below is interactive: use the navigation, flip the switches and open the expanders.

Transcripts are saved as plain text in your Windows user folder for 30 days. Password fields and other protected targets are never saved.

2. What is wrong with the current window

  • Six different ways to show a setting. Bordered checkbox cards, plain checkboxes, radio lists, fieldsets, fact grids and "model-row" cards all sit on the same pages. Nothing looks like a row you can scan.
  • Mixed save models. The shortcut and history need a Save button. Every other control applies at once. A user cannot tell which is which.
  • Sections with no control. "Dock", "Recording behaviour", "Language" and "Protected targets" are headings over one paragraph. Each page also opens with an uppercase eyebrow, a large title and an intro sentence.
  • Model cards for an install the app does not do. Transcription shows a card with Install, Cancel, Remove, a confirm checkbox and a nine-field Technical details box. The installer provisions the model, and an in-app setup path is a settled "no".
  • Controls in the wrong place. Quit is on General in a red "danger zone". Retry is on Output. The diagnostic log is under Output & Privacy. Advanced lists nine runtime facts, then repeats them as raw values.
  • Too many hues. Sage-tinted greys, rust accent, coral logo mark, amber warnings, pink danger tints on whole cards, and a blue focus ring. Red-tinted cards appear on pages where nothing is wrong.

4. Rules for the rework

Layout

  1. A page is a title, then groups. A group is a small label over one card. A card holds rows.
  2. A row has a name, at most one short line under it, and its control on the right.
  3. Every change applies at once. A change that needs consent opens a dialog. There is no Save button.
  4. Status appears in one of two places: a word with a mark under the row name, or an InfoBar at the top of the page.
  5. Technical values live only in Advanced → Technical details.

Palette

surface #f3f3f3
card #ffffff
text #1a1a1a
muted #5c5c5c
accent #0f6cbd
danger #c42b1c

Neutral greys with no tint, one accent for the selected page, switches and primary buttons, and red only for destructive buttons and errors. The dock keeps its own --hud-* palette, and --recording keeps its one meaning.

What must not change

  • Every failure code still has catalog copy at the top of Transcription.
  • "Runs on" reads the worker's device, never the pack.
  • An unanswered read shows "unknown", never a default that claims a state. The shortcut row stays disabled until its status is read.
  • Engine switch and restart report success only when the engine reports ready.
  • History consent names plain text on disk; deleting saved history names its scope and keeps this session's list.
  • The navigation stays a vertical tablist with arrow, Home and End keys. Controls stay 32 px tall inside a 40 px row target or larger. Switches show On/Off in words.
  • docs/UI-GUIDE.md "Information architecture" and "Design tokens" change in the same commit as the code.

5. Owner decisions before the rework

  1. Remove the delivery radios. Inferred from code: they only choose whether Settings shows a "Copy last transcript" button.
  2. Remove Install, Cancel and Remove for the model from Settings. The installer owns this.
  3. Remove the legacy credential rows.
  4. Accent colour. Blue (proposed) or the current rust. Use the toggle above the window to compare.
  5. Shortcut entry. "Change" captures the next key press instead of a typed text field. Also: merge Re-test into Restart engine.
